# Implementation Plan: testbench-dialect-normalization

## Overview

Language: TypeScript, matching the existing packages.
No language choice is open - design.md names concrete modules in `app/tools`, `app/agent`, and `app/eval`.

The build order below is a CORRECTNESS CONSTRAINT, not a preference, and it comes from four separate places.

**1. The accounting lands first (Requirements 1, 2, 3), before any normalizer work.**
`clarification-answers.md` Q1, Answer A, orders it that way because the accounting defects have no independent product value and nothing else in this spec is measurable until they land.
A campaign run with the normalizer but without the accounting would produce another uninterpretable 259/2.
Requirement 1's defect lives in `#repairIfTriggered`, which Requirement 7 later deletes, and design.md's Overview subsection "The overlap between Requirement 1 and Requirement 7" states why that is not a reason to skip either: the fix lands at BOTH trigger points (task 1.2 for the precheck point, task 1.5 for the control point), and only then is one point deleted (task 10.2), which also deletes `mergeRepairProvenance` rather than leaving a seam whose second argument is a constant.

**2. The scanner move lands before any rule that depends on it.**
`app/tools/verilog/source-mask.ts` is an EXTRACTION of the existing private `scanSource` / `SourceMask` from `app/eval/corpus/verilog-mutation.ts`, plus one new `endMode` field.
It is a pure move: `verilog-mutation.ts` keeps identical behaviour, imports the moved module, and no copy of the scanner is left behind.
Task 3.1 does that and nothing else, so a rule written against the mask is written against one owner rather than two.

**3. The identity change and the hash re-pin are two separate tasks, in that order.**
Task 12.1 folds `NORMALIZER_VERSION` into the Config_Identity, which is EXPECTED to fail the two pinned hash assertions.
That failure is the source of the new values, so task 12.2 reads them from the observed failure output and pins them.
A pre-computed or guessed hash would produce a test whose obvious "fix" is to paste whatever the code printed, which passes even when the fold-in silently did not happen.

**4. The comment-as-whitespace fix (group 13) lands before the fixtures are copied (group 14).**
A fixture ENCODES EXPECTED BEHAVIOUR.
Committing fixtures generated by a normalizer that demonstrably turns a compiling source into a non-compiling one would convert a confirmed bug into a passing regression test that defends it.
Three defects were confirmed empirically against Icarus Verilog 13.0 (`iverilog -g2012`) and against the real compiled `normalizeDialect`, and they share one root cause: an adjacency scan that treats a comment span as an opaque barrier rather than as whitespace.
In Verilog a comment is lexically equivalent to whitespace and is stripped before the parser sees the token stream, confirmed directly: `begin // c` newline `: blk` compiles at exit 0, and `begin /* c */ : blk` compiles at exit 0.
So group 13 fixes the three sites, collapses the duplicated `declaredNamesAfter` to one owner, bumps `NORMALIZER_VERSION` 1 -> 2, and re-pins the two config hashes; only then does group 14 copy and index the fixtures, at 29 / 7 / 4.

**5. The fixture suite (group 14) lands BEFORE the rule fix (group 15), which is the REVERSE of the group 13 / group 14 ordering, for a reason worth stating.**
Task 14.2 measured the `unnamed-begin-declaration` rule at **0 of 29** fixtures fixed: it fires on 25 of 29, inserting its label, and the first `syntax error` lands on the identical line before and after.
The original calibration was a confounded experiment - it varied the label and the declaration's POSITION together and credited the label - and the real discriminator is position relative to the first statement of the block.
Group 13's defect was a confirmed FALSE REWRITE, which a fixture would have frozen as expected behaviour, so the fix had to land first.
This one is a confirmed NO-OP, which a pinned count states honestly: the suite lands asserting 0 of 29 as a DOCUMENTED KNOWN-FAILING state, and group 15 flips that pin to its achieved number - which it has, to a MEASURED 25 of 29, taking the committed fixtures to 28 of 40 fixed.
That makes the suite the regression test FOR the fix rather than a claim about it, and it is assertion 7's own "a rule that silently stops firing changes a number" mechanism starting at 0 instead of at 29.
`clarification-answers.md` records the decision as Q1 Answer A and Q4 Answer A of `task-14.2-questions.md`.

Where the 27 correctness properties sit: each property test is placed next to the implementation it validates, and the meaning-preservation cluster (Properties 1, 2, 5, 6, 7, 8, and 18) is gathered into task group 7 as its own group, because Requirement 5 is Council B's largest named risk and asserting it as a group is what stops "it compiles" from being read as "it works".

One deliberate split, stated so it does not read as a gap.
The in-memory half of Requirements 1, 2, and 3 lands in group 1, first, as ordered.
The PERSISTED half (Requirement 3.11 and 3.12 in the Results_Log, and Requirement 1.7 and 3.13 in the Sweep_Summary) lands in group 12 with the single `RESULTS_SCHEMA_VERSION` 11 -> 12 bump, because that same bump also carries Requirement 5.10's Check_Name_Visibility_Signal and both precedent specs took their schema pins once against finished behaviour rather than twice.

Two facts carried forward from the vault, still true here:

- `npx tsc -b app/test` is package-wide and fails on unrelated in-progress sibling test files, so per-task type checks use `npx tsc -b` at the root and the suite is run at the checkpoints.
- A property arbitrary must GENERATE a newly required field, never pin it. `normalization: NormalizationProvenance` is REQUIRED on `VerifiedModule`, `UnverifiedModule`, and `InstrumentRefusedModule`, and `RepairProvenance` becomes a discriminated union. Task 5.1 exists partly to stop every existing fixture from silently pinning an unnormalized baseline and weakening the properties that vary it.

Gate commands are run INDIVIDUALLY at every checkpoint, never chained, because chained gate commands time out in this workspace.
The test baseline immediately before this spec's changes is 1710 passed / 6 skipped / 0 failed.
The measured state with groups 1 through 13 and task 14.1 complete is 1717 passed / 6 skipped / 0 failed.
The final measured state at task 18 is 1883 passed / 6 skipped / 0 failed, and the dominant part of the net rise is task 14.2's fixture suite; the chain including every deletion is recorded in task 18.
